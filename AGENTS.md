# Правила фронтенд-проекта

Этот профиль рассчитан на проекты, которые выбрали указанный ниже стек. Для существующего проекта сначала сверь профиль с его архитектурой и локальными инструкциями.

## Стек и границы изменений

- Используй React, Vite, TypeScript, Effector, Atomic Router, Yarn, Feature-Sliced Design, React Hook Form и Zod.
- Без явного указания пользователя не вводи styled-components, shadcn/ui, Redux, MobX, Zustand, Recoil, React Router, Next.js, SCSS-архитектуру или Tailwind CSS. Для управления зависимостями и запуска команд используй Yarn, не npm, pnpm или bun.
- Выполняй только запрошенную задачу. Переиспользуй существующий код; не создавай абстракции и инфраструктуру без реальной необходимости.
- Самостоятельно работай в рамках принятой архитектуры, включая добавление нужных страниц и маршрутов. Изменение архитектуры требует явного поручения; если необходимое архитектурное решение отсутствует или неоднозначно, уточни его у пользователя.

## Архитектура FSD

Порядок слоёв сверху вниз: `app → pages → widgets → features → entities → shared`.

- `app` — запуск, провайдеры и конфигурация приложения; `pages` — страницы; `widgets` — крупные самостоятельные блоки; `features` — действия пользователя; `entities` — бизнес-сущности; `shared` — независимые от предметной области UI и инфраструктура.
- Импорты между слоями направляй только вниз. Разные слайсы одного слоя не должны импортировать друг друга; внутри слайса импорты разрешены.
- В `app` и `shared` находятся сегменты без слайсов. Импорты между их сегментами разрешены, циклические зависимости — нет.
- Создавай слои, слайсы и сегменты по необходимости. Не добавляй пустые папки и дополнительные слои.
- Каждый слайс предоставляет публичный API через `index.ts`. Потребители используют этот API, а не внутренние файлы.
- В `shared` публичный API принадлежит отдельному сегменту: `@/shared/form`, `@/shared/api`, `@/shared/ui/`. Общий `shared/index.ts` не нужен.
- Компоненты общего UI импортируй только из `@/shared/ui/`, через `src/shared/ui/index.ts`; пути вроде `@/shared/ui/button` запрещены.
- Между слайсами используй алиас `@/`. Внутри слайса или общего сегмента используй относительные импорты непосредственно в файлы, без собственного `index.ts`.
- Не создавай generic repositories, factories и универсальные сервисы без явного запроса.

## Код и именование

- Папки и файлы, кроме файлов React-компонентов: `kebab-case`. React-компоненты и их файлы: `PascalCase`, например `UserCard.tsx`.
- Хуки: `useSomething`; Effector-сторы: `$storeName`; события: `actionPerformed`; эффекты: `actionFx`.
- Фиксированные константы уровня модуля: `UPPER_SNAKE_CASE`. Само объявление `const` не требует верхнего регистра: локальные значения, функции и объекты с данными именуй в `camelCase`.
- Избегай `any`; если он временно неизбежен, добавь TODO с причиной. Предпочитай явные доменные типы: `interface` для доменных моделей, `type` для объединений, mapped types и вспомогательных типов.
- Если форму данных задаёт Zod schema, выводи тип из неё, не дублируй определение.
- Один файл — одна основная ответственность. Избегай файлов больше 300 строк и глубоко вложенного JSX.

## UI, состояние и данные

- Бизнес-логика принадлежит Effector-моделям рядом с соответствующей предметной областью. В React допустимо локальное состояние представления. Не используй React Context как глобальное хранилище и не вводи другой менеджер состояния.
- Данные API получай через сервисы `shared/api`. Компоненты, фичи, сущности и модели не импортируют JSON-моки напрямую; это деталь реализации сервиса.
- Доменный запрос проходит цепочку: действие UI → событие модели → эффект → сервис `shared/api`.
- Значения полей, dirty/touched и клиентская валидация принадлежат RHF; состояние сценария и серверных операций — Effector. Не дублируй значения формы в сторах.
- Стили компонентов — соседние CSS Modules, дизайн-токены — общие CSS-переменные. Сохраняй установленный подход; не вводи вторую систему стилей или UI-библиотеку ради оформления.
- Глобальный CSS ограничен reset, шрифтами, токенами, темами и базовыми стилями документа.

## Запуск и проверка

- Установка зависимостей: `yarn install`; разработка: `yarn dev`; проверка TypeScript и production-сборка: `yarn build`; просмотр сборки: `yarn preview`.
- После изменений кода или конфигурации запускай `yarn build`. Для изменений только инструкций проверяй их структуру, ссылки и согласованность с проектом; сборка приложения не требуется.
- Если в `package.json` настроены тесты или линтер, запускай проверки, относящиеся к задаче. Не заявляй о выполнении отсутствующих проверок и не добавляй инструменты вне задачи.
