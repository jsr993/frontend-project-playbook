# API и моки в ВКС

## Граница доступа к данным

- Перед изменением проверь существующие сервисы и их потребителей. На момент переноса правил `shared/api` ещё не создан; добавляй его только при появлении задачи на данные.
- Сервисы размещай в `src/shared/api/`, JSON-моки — в `src/shared/api/mock/`. Публичные сервисы и необходимые типы экспортируй через `shared/api/index.ts`.
- JSON-мок импортируется только реализацией сервиса. Компоненты, features, entities и Effector-модели обращаются к публичному API сервисов, а не к JSON.
- Сохраняй сервисы независимыми от моделей, UI и верхних слоёв FSD.

## Реализация сервиса

1. Определи минимальный типизированный контракт операции: параметры и результат, нужные текущему потребителю.
2. Скрой источник данных внутри сервиса. Для мокового сервиса сохраняй асинхронный контракт, чтобы последующая замена на HTTP не требовала изменения UI и модели.
3. Подключай сервис к доменному эффекту. Цепочка запроса: действие UI → событие модели → эффект → сервис.
4. При замене моков на backend сохраняй публичный контракт, когда это возможно. Ошибки передавай вызывающему эффекту, чтобы модель могла отразить их в UI.

Не создавай без явного запроса generic repositories, абстрактные API-клиенты, DI-контейнеры, универсальные request factories и сложные кеширующие слои. Для текущей задачи предпочитай простые явные функции сервисов.

## Проверка

Проверь, что потребители импортируют публичный API, моки остаются внутренней деталью, а интерфейс сервиса допускает замену источника данных. После изменения кода выполни `yarn build`.
