# Effector в ВКС

## Размещение и события

- Перед изменением найди модель владельца сценария и её публичный API. Модель может быть файлом `model.ts`, каталогом `model/` или файлом `*.model.ts`; не переноси её только ради унификации структуры.
- Новую бизнес-логику размещай рядом с её владельцем в `entities`, `features` или `pages`. В `shared` оставляй только действительно общую инфраструктуру.
- Держи модели предметными и небольшими; не объединяй несвязанные домены в одно глобальное хранилище.
- Называй события по действию или моменту жизненного цикла: `pageMounted`, `formSubmitted`, `entrySelected`.
- Различай намерение и успешное завершение: `entryDeleteRequested` запрашивает удаление, `entryDeleted` сообщает об успехе.
- Используй явные события и эффекты. Сторы начинаются с `$`, эффекты заканчиваются на `Fx`.

## Асинхронные операции

- React передаёт намерение в событие модели. Модель запускает эффект, эффект обращается к сервису `shared/api`.
- Не выполняй доменные API-запросы из компонентов и не импортируй JSON-моки в эффекты.
- Для операций, влияющих на UI, предоставляй состояние загрузки и ошибки. Переиспользуй `effect.pending`, если оно соответствует нужной операции, вместо дублирующего стора.
- Отражай успешное завершение и ошибку через модель; не объявляй операцию успешной до завершения эффекта.
- При подключении UI используй существующий в проекте подход `effector-react`. Локальное состояние представления может оставаться в React.
- В формах модель владеет open/close, submit, pending, серверной ошибкой и данными options. Поля, dirty/touched и клиентская валидация остаются в RHF.

## Проверка

Проверь направление FSD-импортов, публичный API модели, связь UI-события с эффектом и обработку loading/error. После изменения кода выполни `yarn build`.
